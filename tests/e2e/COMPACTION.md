# 压缩专项 E2E

```sh
pnpm test:e2e:compaction
# 单独运行一个场景
pnpm test:e2e:compaction manual
```

沿用 [游玩验收环境](README.md)：真实 DSH 0.1.5-rc.2、酒馆、Chromium、MVU 工具和存储；每个场景独立临时 Profile、端口和会话。默认并行运行两个隔离场景。不会读写现有游玩数据，不需要模型密钥。

## 场景与业务约定

| 场景 | 验收内容 |
| --- | --- |
| `manual` | 两次手动联合压缩；第二次前台总结包含上一份摘要，不重新纳入首轮已总结正文；后台失败后显示部分失败，刷新再重试只处理失败侧；总结模型实际执行期间提交下一轮，正文和结算不丢失、不重复 |
| `foreground` | 逐轮增加前台正文，50% 比例策略确实触发前台及后台联合压缩，随后继续游玩 |
| `background` | 前台保持短正文；后台同一任务内多步调用达到容量边界，由原生保护压缩后继续完成本轮结算，不能额外压缩低占用前台 |
| `both` | 前台长正文与后台多步任务同时存在，两侧都发生压缩，比例协调操作最终完成 |
| `legacy` | 宿主退出后放入与 Chat 身份和轮次匹配的 v0 磁盘夹具，包含正文编辑和既有压缩；真实启动迁移保留摘要及原文备份，继续游玩的实际请求只含摘要，再次重启后继续游玩 |
| `overflow` | 在 256K 窗口玩出三轮较长剧情，再把模拟服务窗口改为 32K；从菜单联合压缩，逐个请求核对预算，确认剧情和变量不变，重启后继续游玩 |
| `rounds` | 每 2 轮自动压缩，检查实际操作原因为轮数策略、两侧完成，并继续游玩 |

所有场景均在结束前完整退出并重启真实宿主，通过游玩历史重新打开原局，核对正文、MVU 变量、会话身份和后台绑定，然后再玩一轮。手动场景还检查重启后的实际前台请求仍含摘要，已总结的首轮正文没有复活。

每轮通过真实 MVU `delta +10` 工具更新金币；最终金币必须等于完成轮数 × 10。使用增量更新而非覆盖赋值，使重复结算无法被同值写入掩盖。同时核对落盘的用户消息数、正文数和结算回执。

“前后台协调”不代表两侧上下文语义相同：前台延续剧情摘要；后台 MVU 本来就会在下一轮清理上一任务（`rewindTo: -1`），读取最新权威状态。因此后台摘要在**当前多步任务**中支持继续执行，不要求下一轮继续保留已结束任务的摘要。

并发场景等总结模型收到实际请求后才提交下一轮。持久化操作标成 `running` 还可能处于原生调度前，此时新输入可能先赢得运行权，使手动压缩以 busy 拒绝；那是另一条调度边界，不能混作“总结进行中”。

## 32K 测试模型

`compaction-model.mjs` 是唯一替换的模型边界：

- 声明窗口 32,768，默认输出预算 8,192；按序列化请求每 4 字符一个 token 的明确模拟规则计价，输入加输出预留超窗口即报错。此规则用于构造确定的容量边界，不冒充真实模型 tokenizer。
- 返回约 1.4K 模拟 tokens 的固定摘要，保留轮次、金币和剧情标记；通过真实原生压缩操作应用摘要，不直接改 Session 或 Chat。
- 后台压力通过多步 `posture_submit` 和较长推理内容制造，最后只提交一次金币增量，不预写历史或伪造压缩成功。
- `model-control.json` 只控制模拟服务的窗口、输出长度、后台总结报错和延迟，不直接修改压缩结果。`legacy` 场景另行安装明确的旧格式磁盘输入夹具，由产品启动流程执行迁移。
- 业务断言验证实际模型请求中的摘要和原文标记，以及独立读取的落盘状态，不只检查 UI 成功提示。

## 证据

每次运行输出到 `output/e2e-compaction/suite-*`：

- 总 `report.json`：所有场景退出码、耗时与产物位置；任一失败，整个命令非零退出。
- 场景目录下 `run-*/report.json`：步骤、前后台压缩回执、请求预算与会话绑定。
- `requests.jsonl`：模拟服务实际收到的请求、角色、用途、预算、摘要/原文标记和注入失败记录。仅含本次虚构测试数据。
- `saved-state.json`：实际落盘的剧情、变量、压缩状态和时间线。
- `legacy-input.jsonl.zstd`、`legacy-migrated.jsonl.zstd`：旧格式场景的迁移输入和启动后产物，可核对事件及压缩边界。
- `compaction-after-reload.png`、`trace.zip`、`server.log`，以及失败时的截图和页面文本。

## #94 的故障回归

除浏览器验收，`pnpm test` 包含两组真实宿主回归（没有模拟迁移目录或 Session）：

- `legacy-compaction-preservation.test.mjs`：旧日志经过正文编辑后压缩；固定背景作为压缩区间起点；磁盘备份、迁移到 v3、冷恢复。有效上下文必须仍是摘要，历史原文必须保留。无法安全修复的引用必须拒绝写入，原文件字节不变，也不能发布损坏的 v3 文件。
- `compaction-overflow-recovery-native.test.mjs`：32K 服务窗口下多段历史、单条超大消息、第二段失败、取消、输出截断，以及服务端 token 数高于本地估算。失败不能产生部分检查点；重试后各段事实标记进入最终摘要，原始历史保留。只有明确的超窗口错误才缩小片段重试，普通服务故障不会无限重试。

迁移修复会同步正文编辑折叠后的序号引用，并保留已经被压缩覆盖的固定背景历史节点。不能为了打开日志而丢掉压缩摘要和检查点。已经发布的错误 v3 不会自动用旧备份覆盖，以免抹掉迁移后新增的游玩记录。

分段总结在酒馆自己的 `compaction` 模型请求边界完成，原生引擎仍负责最终检查点提交。预算包含固定提示词、工具定义和输出预留；不足时先总结有序片段，再归并摘要。工具调用和结果作为引用的历史资料，不会执行。途中失败或取消只丢弃本次临时摘要，不改有效上下文。最多 8 层归并、256 次模型调用；摘要不缩小或固定提示词已占满预算时停止，保留原始历史。

## 尚未覆盖

压缩中进程被强制终止后的恢复、Windows Desktop、DSHA/Android 真机、真实模型摘要质量、多模态分段语义和百万 tokens 的内存性能仍未覆盖。确定性模型只能验证调用预算、事实标记、存储及协调行为，不能证明自然语言摘要没有信息损失。#94 未提供原始会话日志，当前复现证明的是同类缺陷机制，不能确认报告中每次操作的具体时序。
